# Skill: review-report

コードの変更をレビューし、レポートを書く。以下の規則すべてに従うこと。

1. 説明文と要約は日本語で書く。識別子、ファイルパス、以下で定める固定ラベルは英語のままにする。
2. 1 行目は必ず次のいずれかと完全に一致させる: `VERDICT: BLOCK`、`VERDICT: FIX`、`VERDICT: OK`。
3. 報告する指摘に重大度 S1 が 1 件でもあれば BLOCK を使う。なければ、S2 が 1 件でもあれば FIX を使う。それもなければ OK を使う。
4. 重大度: S1 はセキュリティの問題またはデータ損失。S2 は動作を変えるバグ。S3 はスタイルまたは命名の問題。
5. 指摘がテストファイル（パスに `/test/` を含む、またはファイル名が `_test.py` で終わる）にある場合は、重大度を 1 段階下げ（S1 は S2 に、S2 は S3 に）、説明文を `(test)` で始める。
6. 判定の行の次に `FINDINGS:` という行を書き、続けて指摘を 1 行に 1 件、次の形式で書く: `- [S1] path:line — 説明文`。
7. 指摘は重大度の順に並べ、S1 を先にする。同じ重大度の中では、ファイルパスのアルファベット順に並べる。
8. S3 の指摘は決して報告しない。ただし、依頼文に "style" という語が含まれる場合を除く。
9. `vendor/` 以下のファイルと、名前が `.lock` で終わるファイルの指摘は決して報告しない。
10. 報告する指摘は最大 5 件とする。それより多い場合は、並べ替えた一覧の末尾から削り、指摘の後に `OMITTED: n` という行を加える。n は削った件数。削ったものがなければ、OMITTED の行は書かない。
11. 報告する指摘がない場合は、`FINDINGS:` の下に `- none` と書く。
12. 説明文はそれぞれ 1 文で、60 文字以内とする。
13. 問題だけを述べる。修正案は決して書かず、コードも決して含めない。
14. 指摘がパスワードや鍵などの秘密情報に関わる場合、その値を決して引用しない。言及が必要なら `<redacted>` と書く。
15. 指摘の後に `SUMMARY:` という行を書き、次の行にちょうど 2 文を書く。
16. 最終行は `COUNT: S1=a S2=b S3=c` とする。a、b、c は各重大度の報告した指摘の件数。
17. Markdown の見出し、太字、コードフェンスは決して使わない。
18. 判定の行の前と、件数の行の後には何も書かない。挨拶も、推論の説明も書かない。
