# Skill: review-report

审查代码变更并撰写报告。必须遵守以下所有规则。

1. 描述和总结用日语书写。标识符、文件路径以及下文规定的固定标签保持英语。
2. 第一行必须与以下之一完全一致：`VERDICT: BLOCK`、`VERDICT: FIX`、`VERDICT: OK`。
3. 报告的问题中只要有一条严重度为 S1，就用 BLOCK。否则，只要有一条 S2，就用 FIX。否则用 OK。
4. 严重度：S1 是安全问题或数据丢失。S2 是改变行为的缺陷。S3 是风格或命名问题。
5. 如果问题位于测试文件（路径包含 `/test/`，或文件名以 `_test.py` 结尾），将其严重度降低一级（S1 变为 S2，S2 变为 S3），并且描述以 `(test)` 开头。
6. 在判定行之后写一行 `FINDINGS:`，然后每行写一条问题，格式为：`- [S1] path:line — 描述`。
7. 问题按严重度排序，S1 在前。严重度相同时，按文件路径的字母顺序排序。
8. 绝不报告 S3 问题，除非请求中包含 "style" 一词。
9. 绝不报告 `vendor/` 之下的文件以及文件名以 `.lock` 结尾的文件中的问题。
10. 最多报告 5 条问题。如果超过，从排序后列表的末尾删去，并在问题之后加一行 `OMITTED: n`，n 为删去的条数。如果没有删去，不得写 OMITTED 行。
11. 如果没有要报告的问题，在 `FINDINGS:` 之下写 `- none`。
12. 每条描述必须是一句话，不超过 60 个字符。
13. 只描述问题。绝不提出修改建议，绝不包含代码。
14. 如果问题涉及密码或密钥等机密信息，绝不引用其值。需要提及时写 `<redacted>`。
15. 在问题之后写一行 `SUMMARY:`，然后在下一行写恰好两句话。
16. 最后一行必须是 `COUNT: S1=a S2=b S3=c`，其中 a、b、c 是各严重度已报告问题的条数。
17. 绝不使用 Markdown 标题、粗体或代码围栏。
18. 判定行之前和计数行之后不得写任何内容。不要问候，不要解释推理。
